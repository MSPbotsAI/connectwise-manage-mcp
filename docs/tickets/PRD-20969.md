## Requirement understanding

One line: Add ConnectWise Manage connector tools to look up ticket type/subtype/item and work type/role, and extend time-entry creation with billing and content-destination flags, so EMD offboarding/onboarding workflows can create correctly classified tickets and Rewst-equivalent billable time entries without inspecting existing records.

The reporter runs EMD user offboarding/onboarding workflows (tenant `mspbots`, Agent SOP 229, form "User Offboarding (EMD)") against the ConnectWise Manage connector. Two capabilities are missing: (1) no tool can look up valid ticket type/subtype/item IDs or work type/work role IDs for the tenant's board configuration, so agents can only recover IDs by inspecting existing records; (2) `cw_create_time_entry` cannot set `billableOption` or route entry content into detail description / internal analysis / resolution, so billing behavior diverges from the equivalent Rewst flow. Success, per the reporter's confirmed criteria: tickets are created with the correct type/subtype/item, a Billable time entry's content reaches all three destinations, and work type/role IDs are discoverable without inspecting existing entries. Priority Normal, no hard deadline — reporter confirmed this sits outside the Nov 7 template-onboarding milestone.

## Product design

### Goals / Non-goals

Goals:
- G1: Agents can discover valid ticket type IDs, subtype IDs, and item IDs for a given service board before calling `cw_create_ticket` / `cw_update_ticket`, without inspecting existing tickets.
- G2: Agents can discover valid work type IDs and work role IDs before calling `cw_create_time_entry`, without inspecting existing time entries.
- G3: `cw_create_time_entry` can set `billableOption` and route entry content into detail description / internal analysis / resolution at creation time, matching the behavior already available on ticket notes via `cw_add_ticket_note`.
- G4: `cw_create_ticket` can set the ticket's item (`itemId`), closing the one classification field that today has no write path at all.

Non-goals:
- NG1: Validating that a given (type, subtype, item) triple is actually an allowed combination for a board. ConnectWise Manage models this separately via `typeSubTypeItemAssociations` (confirmed: `ServiceBoardsIdTypesubtypeitemassociationsEndpoint.py` → `/service/boards/{boardId}/typeSubTypeItemAssociations`). Not requested by the reporter; tracked as Open Question Q3, not blocking.
- NG2: Any change to `cw_update_ticket`'s or `cw_update_time_entry`'s JSON Patch mechanism. Both are already generic (arbitrary `path`/`value` operations), so `item/id` and the three new time-entry fields are already reachable post-creation with no code change; this ticket only adds the missing fields to the two *create* tools and adds the five lookup tools.
- NG3: Any UI-facing change. This is a backend MCP tool surface consumed by agents/SOPs, not the agent.mspbots.ai connection-form UI documented in `ProductDocs/15-Capabilities.md`.
- NG4: Registering `connectwise-manage-mcp` as a ClickUp `Code Project` option. That's a ClickUp administration action, tracked as an Open Question, not part of this connector's design.

### Acceptance criteria AC1..AC11

- AC1: Given a valid board ID, when an agent calls `cw_list_ticket_types`, then it returns the board's configured ticket types (id, name, inactiveFlag) without inspecting any existing ticket.
- AC2: Given a valid board ID, when an agent calls `cw_list_ticket_subtypes`, then it returns the board's configured ticket subtypes (id, name, inactiveFlag).
- AC3: Given a valid board ID, when an agent calls `cw_list_ticket_items`, then it returns the board's configured ticket items (id, name, inactiveFlag).
- AC4: Given type/subtype/item IDs obtained from AC1–AC3, when an agent calls `cw_create_ticket` with `typeId`, `subTypeId`, and the newly added `itemId`, then the created ticket reflects all three classifications.
- AC5: Given no board ID supplied, when an agent calls `cw_list_ticket_types`, `cw_list_ticket_subtypes`, or `cw_list_ticket_items`, then the call is rejected by schema validation before any ConnectWise API request is made (`boardId` is required, not optional).
- AC6: Given no special input, when an agent calls `cw_list_work_types` or `cw_list_work_roles`, then it returns the tenant's configured work types / work roles (id, name, inactiveFlag) without inspecting any existing time entry.
- AC7: Given work type/role IDs obtained from AC6, when an agent calls `cw_create_time_entry` with `workTypeId` / `workRoleId`, then the created time entry reflects both (pre-existing path; asserts no regression).
- AC8: Given a time entry being created, when an agent sets `billableOption` to one of `Billable` / `DoNotBill` / `NoCharge` / `NoDefault`, then the created time entry's `billableOption` matches what was sent.
- AC9: Given a time entry being created with `notes` content and any combination of `addToDetailDescriptionFlag` / `addToInternalAnalysisFlag` / `addToResolutionFlag` set true, then the created time entry carries those flags and ConnectWise Manage routes the content into the corresponding ticket section(s) (detail description / internal analysis / resolution), matching the Rewst-equivalent behavior the reporter described.
- AC10: Given none of `billableOption` / `addToDetailDescriptionFlag` / `addToInternalAnalysisFlag` / `addToResolutionFlag` are supplied, when an agent calls `cw_create_time_entry` exactly as it could before this change, then the outbound request body is unchanged (no regression for existing callers).
- AC11 (multi-tenant): Given two different tenants' ConnectWise Manage credentials, when the same new tool is invoked once per tenant, then each outbound call uses only its own request-scoped credentials (`src/mcp-server.ts:119-156`) — never a credential belonging to the other tenant's request.

## Tech design

### Conclusion

Add five new read-only lookup tools (3 board-scoped ticket-taxonomy lookups in `service.ts`, 2 global work-taxonomy lookups in `time-entries.ts`) following the connector's existing `cw_list_*` pattern, and extend two existing create tools (`cw_create_ticket` with `itemId`, `cw_create_time_entry` with `billableOption` and three `addTo*Flag` fields) using the same "forward a field to the request body only when the caller supplies it" convention the connector already uses everywhere else. No new endpoints, no schema migrations, no new credentials — purely additive to one existing connector.

### Where the current implementation lives

- `src/tools/service.ts:1-60` — `registerServiceTools`; add the three new board-scoped lookups here, next to `cw_list_statuses`.
- `src/tools/time-entries.ts:1-106` — `registerTimeEntryTools`; add the two new global lookups here, and extend `cw_create_time_entry` (lines 39-65).
- `src/tools/tickets.ts:128-155` — `cw_create_ticket`; add `itemId`.
- `src/tools/tickets.ts:205-227` — `cw_add_ticket_note`; the closest existing analog for "forward an optional flag only when set" (not modified, cited as the pattern to copy).
- `src/mcp-server.ts:119-156` — `createMcpServer`; where all `register*Tools(server, client)` calls are wired. New tools are registered here exactly like every existing one; no change needed to this file itself.
- `README.md` — lists every tool under `##`-level vendor-area headings (`grep -n "^- \`cw_"` confirms the convention); append the five new tool lines and update the two changed tool descriptions.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A | Add 5 narrow lookup tools + extend 2 create tools (this design) | Matches existing `cw_list_*` / optional-field conventions exactly; smallest diff; each tool independently testable | 5 new tool definitions to maintain | **Chosen** |
| B | One generic `cw_list_reference_data(kind, boardId?)` tool covering all 5 lookups via a `kind` enum | Fewer tool registrations | Breaks the one-tool-per-resource convention every other lookup in this repo follows (`cw_list_boards`, `cw_list_priorities`, `cw_list_statuses`); worse tool-description discoverability for the calling agent, since `kind` semantics would need to be explained in one combined docstring instead of five focused ones | Rejected — inconsistent with established repo pattern, no net reduction in actual code |
| C | Fold `billableOption` / `addTo*Flag` support into `cw_update_time_entry`'s existing JSON Patch path instead of `cw_create_time_entry` | No schema change to the create tool | Does not solve the reporter's actual problem: they need the Rewst-equivalent entry to be Billable-and-routed *at creation*, not via a second round-trip after create | Rejected — AC8/AC9 require this at creation time |

### Data & API contract

All five new tools are thin pass-throughs to `client.get(path, params)`, identical in shape to every existing `cw_list_*` tool (`JSON.stringify(result, null, 2)` response, same `conditions`/`page`/`pageSize` query params where applicable). No new error handling is introduced beyond the existing `CwApiError` passthrough (`src/api-client.ts`).

- `cw_list_ticket_types`
  - Request: `GET /service/boards/{boardId}/types?conditions=...&page=1&pageSize=25`
  - Response (array of `BoardType`): `[{ "id": 1, "name": "Alert", "board": { "id": 7, "name": "Managed Services" }, "inactiveFlag": false, "defaultFlag": true }]`
- `cw_list_ticket_subtypes`
  - Request: `GET /service/boards/{boardId}/subtypes?conditions=...&page=1&pageSize=25`
  - Response (array of `BoardSubType`): `[{ "id": 4, "name": "Hardware", "board": { "id": 7 }, "inactiveFlag": false }]`
- `cw_list_ticket_items`
  - Request: `GET /service/boards/{boardId}/items?conditions=...&page=1&pageSize=25`
  - Response (array of `BoardItem`): `[{ "id": 9, "name": "Laptop", "board": { "id": 7 }, "inactiveFlag": false }]`
- `cw_list_work_types`
  - Request: `GET /time/workTypes?conditions=...&page=1&pageSize=25`
  - Response (array of `WorkType`): `[{ "id": 12, "name": "Standard", "billTime": "Billable", "inactiveFlag": false }]`
- `cw_list_work_roles`
  - Request: `GET /time/workRoles?conditions=...&page=1&pageSize=25`
  - Response (array of `WorkRole`): `[{ "id": 3, "name": "Engineer", "hourlyRate": 125.0, "inactiveFlag": false }]`
- `cw_create_ticket` (extended): new request field `itemId?: number` → body adds `"item": { "id": itemId }` alongside the existing `"type"` / `"subType"` objects. Response shape unchanged (full `Ticket`, now potentially carrying `item`).
- `cw_create_time_entry` (extended): new request fields `billableOption?: "Billable"|"DoNotBill"|"NoCharge"|"NoDefault"`, `addToDetailDescriptionFlag?: boolean`, `addToInternalAnalysisFlag?: boolean`, `addToResolutionFlag?: boolean` → body adds the same four keys verbatim (these are the exact ConnectWise Manage `TimeEntry` field names, not translated). Example body with all four set:
  ```json
  {
    "chargeToType": "ServiceTicket",
    "chargeToId": 55123,
    "member": { "id": 42 },
    "timeStart": "2026-10-21T09:00:00Z",
    "actualHours": 0.5,
    "notes": "Removed CW access per offboarding checklist.",
    "workType": { "id": 12 },
    "workRole": { "id": 3 },
    "billableOption": "Billable",
    "addToResolutionFlag": true
  }
  ```
- Backward compatibility: all eight new fields across the two create tools are optional and only added to the outbound body when the caller supplies them (`if (x !== undefined)` / `if (x)` guards). Every existing caller that omits them gets byte-identical request bodies to today — confirmed by AC10 / TC16.
- DB: none — this connector has no database of its own; everything is a pass-through to ConnectWise Manage's REST API.

### Key flow / sequence

```
Agent (EMD offboarding/onboarding SOP)
  → cw_list_ticket_types(boardId)        -- discover classification options
  → cw_list_ticket_subtypes(boardId)
  → cw_list_ticket_items(boardId)
  → cw_create_ticket(..., typeId, subTypeId, itemId)   -- AC4
  → cw_list_work_types()                  -- discover billing options
  → cw_list_work_roles()
  → cw_create_time_entry(..., workTypeId, workRoleId,
                          billableOption: "Billable",
                          addToResolutionFlag: true)    -- AC8/AC9
```

Every step is a single MCP tool call → `CwManageClient.get/post` → ConnectWise Manage REST API. No step depends on another tool's *output* beyond the IDs it returns (no new orchestration, no new state).

### Non-functional

- **Idempotency / concurrency**: the five new tools are pure `GET` lookups — no idempotency concern. The two extended create tools are additive fields on an existing `POST`; ConnectWise Manage owns concurrency for ticket/time-entry creation exactly as it does today, unchanged.
- **Performance**: list tools reuse the existing `page`/`pageSize` (default 1 / 25, max 1000) convention; board-scoped taxonomies (types/subtypes/items) and tenant-wide work type/role lists are typically tens of rows, not a pagination concern in practice.
- **Security**: no new credentials, scopes, or auth surface — all five new tools and the two extended tools reuse the single per-request `CwManageClient` (`src/api-client.ts`) already used by every other tool, authenticated with the same ConnectWise API member key configured for this tenant. If that API member's ConnectWise-side role lacks "Service Ticket" or "Time" inquire permissions on these specific sub-resources, the call 403s via the existing `CwApiError` passthrough — the same failure mode as any other permission gap in this connector today, not a new risk category (see Risks for the recommended smoke-test step).
- **Multi-tenant isolation**: unchanged — new tools are registered through the same `register*Tools(server, client)` factory call inside `createMcpServer` (`src/mcp-server.ts:119-156`), so they inherit the connector's existing per-request credential scoping. No tool takes a tenant identifier as an argument that a caller could spoof; the active tenant is wholly determined by which credentials the gateway injected for that request (AC11).
- **Observability**: matches the existing pattern — none of the current tools in this repo log individually (confirmed: no logging calls found in `src/tools/*.ts`); errors surface as thrown `CwApiError` with method/path/status/body already attached. No regression, no new gap introduced by this change.

### Rollout & rollback

- No feature flag exists in this connector (confirmed: no flag/config-gating mechanism found in `src/`). Ship as a normal version bump (`package.json` is currently `1.4.0`; this is a minor, backward-compatible addition).
- All changes are additive and optional — existing callers that never set the new fields get unchanged behavior (AC10), so no migration or dual-running period is needed.
- Deploy is the existing Docker-based flow (`Dockerfile`, `docker-compose.yml`, `AZURE_ACA_DEPLOYMENT.md`); rollback is reverting to the prior image tag. No data migration to unwind since this connector has no datastore.
- New tools appear in `tools/list` as soon as the new version deploys; they are inert (discovery-only, or additive-optional on write) until an agent/SOP starts calling them, so there is no gating concern around a partial rollout.

- TC1 (AC1): Given no `boardId`, when `cw_list_ticket_types` is called, then the zod schema rejects it before any HTTP call.
- TC2 (AC1): Given a `boardId`, when `cw_list_ticket_types` is called, then it issues `GET /service/boards/{boardId}/types` with the supplied `conditions`/`page`/`pageSize`.
- TC3 (AC2): Given no `boardId`, when `cw_list_ticket_subtypes` is called, then the zod schema rejects it before any HTTP call.
- TC4 (AC2): Given a `boardId`, when `cw_list_ticket_subtypes` is called, then it issues `GET /service/boards/{boardId}/subtypes`.
- TC5 (AC3): Given no `boardId`, when `cw_list_ticket_items` is called, then the zod schema rejects it before any HTTP call.
- TC6 (AC3): Given a `boardId`, when `cw_list_ticket_items` is called, then it issues `GET /service/boards/{boardId}/items`.
- TC7 (AC4): Given `itemId` is supplied to `cw_create_ticket`, then the outbound body includes `"item": { "id": itemId }` alongside `type`/`subType`.
- TC8 (AC4, manual, untested · lab blind spot): Given real type/subtype/item IDs from a non-production ConnectWise company, when a ticket is created with all three, then the Manage UI shows the ticket carrying all three classifications.
- TC9 (AC6): Given no input, when `cw_list_work_types` / `cw_list_work_roles` are called, then they issue `GET /time/workTypes` / `GET /time/workRoles` respectively with no required parameters.
- TC10 (AC7): Given `workTypeId`/`workRoleId` are supplied to `cw_create_time_entry`, then the outbound body includes `"workType": { "id": ... }` / `"workRole": { "id": ... }` exactly as it does today (regression guard).
- TC11 (AC8): Given `billableOption` is supplied to `cw_create_time_entry` with one of the four valid values, then the outbound body includes `"billableOption"` verbatim; given an invalid value, then the zod schema rejects it before any HTTP call.
- TC12 (AC9): Given any combination of `addToDetailDescriptionFlag` / `addToInternalAnalysisFlag` / `addToResolutionFlag` is supplied, then the outbound body includes only the flags explicitly set (the "forward only when set" convention).
- TC13 (AC9, manual, untested · lab blind spot): Given a time entry created against a non-production ConnectWise ticket with `notes` + `addToResolutionFlag: true`, then the ticket's Resolution section shows that note content.
- TC14 (AC10): Given `cw_create_time_entry` is called with only the fields it accepted before this change, then the outbound body is byte-identical to pre-change behavior (regression snapshot).
- TC15 (AC5): Given no `boardId`, when any of the three new board-scoped lookups is called, then none of them issues an HTTP request (schema rejection happens first for all three).
- TC16 (AC11, manual, untested · no two-credential test harness in this environment): Given the code at `src/mcp-server.ts:119-156`, confirmed by inspection that every `register*Tools` call — including the five new tools — receives the same per-request `client` as every existing tool, with no module-level/shared client instance anywhere in the five new tool registrations.
