## 需求理解

一句话：在 ConnectWise Manage 连接器上增加工单类型/子类型/条目、工作类型/工作角色的查询工具，并给工时创建接口加上计费与内容去向开关，使 EMD 离职/入职流程能创建正确分类的工单和 Rewst 等效的可计费工时记录，而不必反查现有记录。

提单人在跑 EMD 用户离职/入职流程（租户 `mspbots`，Agent SOP 229，表单 "User Offboarding (EMD)"），调用的是 ConnectWise Manage 连接器。缺两类能力：(1) 没有工具能查出该租户看板配置下合法的工单类型/子类型/条目 id，或工作类型/工作角色 id，agent 只能靠反查已有记录来猜 id；(2) `cw_create_time_entry` 不能设置 `billableOption`，也不能把工时记录的内容写入详细描述/内部分析/解决方案，导致计费行为和 Rewst 的等效流程不一致。按提单人确认的成功标准：工单被创建时带有正确的类型/子类型/条目；一条 Billable 工时记录的内容同步到三处；工作类型/角色 id 不必反查现有记录即可查到。优先级 Normal，无硬性截止日期——提单人已确认这不在 11 月 7 日模板上线里程碑范围内。

## 产品设计

### 目标 / 非目标

目标：
- G1：agent 在调用 `cw_create_ticket` / `cw_update_ticket` 之前，能查出给定看板上合法的工单类型 id、子类型 id、条目 id，不必反查已有工单。
- G2：agent 在调用 `cw_create_time_entry` 之前，能查出合法的工作类型 id、工作角色 id，不必反查已有工时记录。
- G3：`cw_create_time_entry` 在创建时就能设置 `billableOption`，并把内容投递进详细描述/内部分析/解决方案，与 `cw_add_ticket_note` 在工单备注上已有的行为对齐。
- G4：`cw_create_ticket` 能设置工单的条目（`itemId`）——这是今天唯一完全没有写入路径的分类字段。

非目标：
- NG1：校验某个 (类型, 子类型, 条目) 三元组对某个看板是否是合法组合。ConnectWise Manage 用单独的 `typeSubTypeItemAssociations` 建模这件事（已确认：`ServiceBoardsIdTypesubtypeitemassociationsEndpoint.py` → `/service/boards/{boardId}/typeSubTypeItemAssociations`）。提单人没有要求，记在 Open Question Q3，不阻塞。
- NG2：改动 `cw_update_ticket` 或 `cw_update_time_entry` 的 JSON Patch 机制。两者本来就是通用的（任意 `path`/`value` 操作），所以 `item/id` 和三个新工时字段在创建之后已经可达、不需要改代码；本单只给两个**创建**工具补字段，并新增五个查询工具。
- NG3：任何 UI 层面的改动。这是面向 agent/SOP 的后端 MCP 工具层，不是 `ProductDocs/15-Capabilities.md` 里记录的 agent.mspbots.ai 连接表单 UI。
- NG4：把 `connectwise-manage-mcp` 注册成 ClickUp `Code Project` 的选项。那是 ClickUp 管理动作，记在 Open Questions，不属于这个连接器的设计范围。

### 验收标准 AC1..AC11

- AC1：给定一个合法的看板 id，当 agent 调用 `cw_list_ticket_types`，则返回该看板配置的工单类型（id、name、inactiveFlag），不需要反查任何已有工单。
- AC2：给定一个合法的看板 id，当 agent 调用 `cw_list_ticket_subtypes`，则返回该看板配置的工单子类型（id、name、inactiveFlag）。
- AC3：给定一个合法的看板 id，当 agent 调用 `cw_list_ticket_items`，则返回该看板配置的工单条目（id、name、inactiveFlag）。
- AC4：给定从 AC1–AC3 拿到的类型/子类型/条目 id，当 agent 调用 `cw_create_ticket` 并带上 `typeId`、`subTypeId` 和新增的 `itemId`，则创建出的工单同时带有这三项分类。
- AC5：不提供看板 id 时，当 agent 调用 `cw_list_ticket_types` / `cw_list_ticket_subtypes` / `cw_list_ticket_items` 任意一个，则该调用在发出任何 ConnectWise API 请求之前就被 schema 校验拒绝（`boardId` 是必填，不是可选）。
- AC6：不需要特殊输入，当 agent 调用 `cw_list_work_types` 或 `cw_list_work_roles`，则返回该租户配置的工作类型/工作角色（id、name、inactiveFlag），不需要反查任何已有工时记录。
- AC7：给定从 AC6 拿到的工作类型/角色 id，当 agent 调用 `cw_create_time_entry` 并带上 `workTypeId` / `workRoleId`，则创建出的工时记录同时带有两者（这条路径本来就存在；这里断言不回归）。
- AC8：在创建一条工时记录时，当 agent 把 `billableOption` 设成 `Billable` / `DoNotBill` / `NoCharge` / `NoDefault` 之一，则创建出的工时记录的 `billableOption` 与所传值一致。
- AC9：在创建一条带 `notes` 内容的工时记录时，当 agent 设置了 `addToDetailDescriptionFlag` / `addToInternalAnalysisFlag` / `addToResolutionFlag` 的任意组合为 true，则创建出的工时记录带有这些开关，且 ConnectWise Manage 把内容投递进对应的工单板块（详细描述 / 内部分析 / 解决方案），与提单人描述的 Rewst 等效行为一致。
- AC10：`billableOption` / `addToDetailDescriptionFlag` / `addToInternalAnalysisFlag` / `addToResolutionFlag` 均未提供时，当 agent 按这次改动之前就能用的方式调用 `cw_create_time_entry`，则发出的请求体与改动前完全一致（对现有调用方不回归）。
- AC11（多租户）：给定两个不同租户的 ConnectWise Manage 凭据，当同一个新工具分别为每个租户调用一次，则每次调用只使用自己那次请求所携带的凭据（`src/mcp-server.ts:119-156`）——绝不会用到另一个租户那次请求的凭据。

## 技术设计

### 结论

在 `service.ts` 里按既有 `cw_list_*` 写法加三个按看板域定的只读查询工具，在 `time-entries.ts` 里加两个全局域的工作分类查询工具；再给两个既有的创建工具（`cw_create_ticket` 加 `itemId`，`cw_create_time_entry` 加 `billableOption` 和三个 `addTo*Flag`）用这个连接器到处都在用的"调用方传了才写进请求体"的写法扩展字段。没有新接口、没有 schema 迁移、没有新凭据——纯粹是给一个现有连接器做加法。

- `cw_list_work_roles`
  - 请求：`GET /time/workRoles?conditions=...&page=1&pageSize=25`
  - 响应（`WorkRole` 数组）：`[{ "id": 3, "name": "Engineer", "hourlyRate": 125.0, "inactiveFlag": false }]`
- `cw_create_ticket`（扩展）：新增请求字段 `itemId?: number` → body 在既有 `"type"` / `"subType"` 对象旁加 `"item": { "id": itemId }`。响应形状不变（完整 `Ticket`，现在可能带 `item`）。
- `cw_create_time_entry`（扩展）：新增请求字段 `billableOption?: "Billable"|"DoNotBill"|"NoCharge"|"NoDefault"`、`addToDetailDescriptionFlag?: boolean`、`addToInternalAnalysisFlag?: boolean`、`addToResolutionFlag?: boolean` → body 原样加上这四个键（这些就是 ConnectWise Manage `TimeEntry` 的真实字段名，不做翻译）。四个都设置时的请求体示例：
  ```json
  {
    "chargeToType": "ServiceTicket",
    "chargeToId": 55123,
    "member": { "id": 42 },
    "timeStart": "2026-10-21T09:00:00Z",
    "actualHours": 0.5,
    "notes": "Removed CW access per offboarding checklist.",
    "workType": { "id": 12 },
    "workRole": { "id": 3 },
    "billableOption": "Billable",
    "addToResolutionFlag": true
  }
  ```
- 向后兼容：两个创建工具新增的全部 8 个字段都是可选的，只有调用方提供时才会被加进请求体（`if (x !== undefined)` / `if (x)` 守卫）。所有不传这些字段的既有调用方拿到的请求体和今天逐字节一致——由 AC10 / TC16 确认。
- 数据库：无——这个连接器自己没有数据库，一切都是对 ConnectWise Manage REST API 的透传。

### 关键流程时序

```
Agent（EMD 离职/入职 SOP）
  → cw_list_ticket_types(boardId)        -- 查分类选项
  → cw_list_ticket_subtypes(boardId)
  → cw_list_ticket_items(boardId)
  → cw_create_ticket(..., typeId, subTypeId, itemId)   -- AC4
  → cw_list_work_types()                  -- 查计费选项
  → cw_list_work_roles()
  → cw_create_time_entry(..., workTypeId, workRoleId,
                          billableOption: "Billable",
                          addToResolutionFlag: true)    -- AC8/AC9
```

每一步都是单次 MCP 工具调用 → `CwManageClient.get/post` → ConnectWise Manage REST API。除了需要用到上一步返回的 id 之外，没有任何一步依赖另一个工具的其它输出——没有新编排，没有新状态。

### 非功能

- **幂等与并发**：五个新工具都是纯 `GET` 查询——不存在幂等问题。两个被扩展的创建工具只是在既有 `POST` 上加字段；工单/工时记录创建的并发仍然完全由 ConnectWise Manage 自己兜底，和今天一样，没有变化。
- **性能**：查询工具沿用既有的 `page`/`pageSize`（默认 1/25，上限 1000）惯例；按看板域定的分类（类型/子类型/条目）和租户级的工作分类列表通常只有几十行，实际上谈不上分页压力。
- **安全**：没有新凭据、新 scope、新鉴权面——五个新工具和两个被扩展的工具复用的都是本仓库每个工具都在用的同一个按请求生成的 `CwManageClient`（`src/api-client.ts`），用的是该租户配置的同一个 ConnectWise API member key。如果这个 API member 在 ConnectWise 侧的角色缺少对这几个子资源的 "Service Ticket" 或 "Time" 查询权限，调用会经由既有的 `CwApiError` 透传返回 403——这和这个连接器今天任何一处权限缺口的失败方式一样，不是新的风险类别（冒烟测试建议见「风险与依赖」）。
- **多租户隔离**：不变——新工具都是通过 `createMcpServer`（`src/mcp-server.ts:119-156`）里同一个 `register*Tools(server, client)` 工厂调用注册的，天然继承连接器既有的按请求凭据作用域。没有任何工具把租户标识当参数接收、给调用方留下伪造空间;当次请求网关注入了哪个租户的凭据，活跃租户就是哪个（AC11）。
- **可观测性**：和既有模式一致——本仓库现在没有任何工具做单独日志（已确认：`src/tools/*.ts` 里搜不到日志调用）；报错都是通过抛出的 `CwApiError` 浮现，已经带了 method/path/status/body。这次改动不回归、也不引入新缺口。
